# Аудит истории репозитория на секреты

Гейт перед переводом репозитория в public (JWT-52) и регламент проверок после.

Публикация репозитория необратима: клоны, форки и поисковые индексы появляются
раньше, чем успеваешь передумать. Поэтому вопрос «нет ли в истории секрета»
закрывается прогоном сканеров по **всем** коммитам, а не грепом по знакомым
именам переменных: греп находит то, что искали, а утекает обычно то, о чём не
подумали — высокоэнтропийная строка в одноразовом скрипте, ключ в примере,
дамп конфига в отладочном коммите.

## Вердикт

**История чистая.** На 2026-08-25 (`1ec2040`, master) два независимых сканера
дают ноль неразобранных находок. Всё, что они нашли, — демо-значения локальных
стендов, разобранные ниже поимённо.

Ни одного **верифицированного** секрета (trufflehog проверяет находки по сети):
`verified_secrets: 0`.

**PR-рефы (`refs/pull/*/head`) в охвате намеренно.** Коммит, снесённый
force-push'ем с ветки, остаётся доступен на GitHub по ссылке пул-реквеста
неограниченно долго. Проверка «по веткам» такие коммиты не видит — а публика
видит. Их подтягивают явно:

```bash
git fetch origin '+refs/pull/*/head:refs/remotes/origin/pr/*'
```

В этом репозитории PR-рефы дали 6 коммитов сверх достижимых по веткам; находок
в них нет.

## Чем просканировано

Сканеров два, потому что по отдельности каждый слеп в своей половине:

- **gitleaks v8.30.1** — регулярки и энтропия по диффам. Берёт ключеподобный
  мусор любого формата, включая самодельный, но не отличает живой ключ от
  выдуманного.
- **trufflehog 3.97.1** — детекторы под конкретные сервисы плюс **верификация
  находки по сети**. Формат знает хуже, зато отвечает на главный вопрос: этим
  ключом прямо сейчас можно воспользоваться или нет.

Прогон — одной командой, ей же пользуется CI:

```bash
scripts/scan-secrets.sh                 # оба сканера по всей истории
scripts/scan-secrets.sh --reports out   # с JSON-отчётами в ./out
```

Версии образов пиньованы в скрипте: «просканировано последней версией» — не
воспроизводимое утверждение, а sha образа плюс дата — воспроизводимое.

## Что проверено помимо сканеров

Сканеры отвечают на вопрос «нет ли в истории секретоподобных строк». Отдельно
проверено, что не коммитились файлы, которые секретов не содержат по имени, но
содержат по смыслу, — по **всем объектам** всех ссылок, а не по рабочему дереву:

```bash
git rev-list --objects --all | awk 'NF>1{ $1=""; print }' | sort -u | grep -Ei '...'
```

- `AGENTS_INTERNAL.md` (внутренние заметки, доступы) — не коммитился ни разу;
- `.idea/` — не отслеживался ни разу;
- `deployments/prod/.env` и `deployments/prod/k8s/secret.yaml` — не
  коммитились; в репозитории только шаблоны `.env.example` и
  `secret.example.yaml`, и значения секретов в них пустые либо `"замените"`;
- `deployments/load/tokens.json` и `summary.json` (настоящие подписанные JWT с
  нагрузочного прогона) — не коммитились;
- файлов с расширениями `.pem`, `.key`, `.p12`, `.pfx`, `.jks`, `.ppk` и
  подобных в истории нет вовсе.

Всё перечисленное закрыто `.gitignore`, но `.gitignore` защищает только от
будущего: файл, попавший в индекс раньше правила, остаётся в истории навсегда.
Поэтому проверка по объектам, а не по текущим правилам игнора.

## Что этот отчёт не закрывает

- **Недостижимые объекты на стороне GitHub.** Локальный `git fsck` их видит,
  но сканеры ходят по ссылкам. PR-рефы — основной канал утечки такого рода —
  в охвате (см. выше); остаточный хвост (объекты из удалённых форков,
  недостижимые из любого рефа) убирается только обращением в поддержку GitHub
  и в этом репозитории беспредметен: чистых коммитов не находилось вовсе, так
  что и переписывать историю не потребовалось.
- **Будущие коммиты.** Разовый аудит протухает с первым же пушем — поэтому он
  и превращён в CI-гейт, см. ниже.
- **Секреты, не похожие на секреты.** Ни один сканер не найдёт внутренний
  hostname или ФИО в комментарии. Это вопрос ревью, а не регулярок.

## Регресс: проверка в CI

Гейт держит [`.github/workflows/secrets.yml`](../../.github/workflows/secrets.yml):
тот же `scripts/scan-secrets.sh` на каждый PR, на пуш в `master`, еженедельно по
расписанию и по кнопке. Находка роняет пайплайн, JSON-отчёты выкладываются
артефактом (`secret-scan-reports`, 14 дней) — по ним разбирают находку, не
переспрашивая у лога.

Один и тот же скрипт локально и в CI — чтобы набор флагов и allowlist'ы не
разъезжались между разработчиком и раннером по построению, а не потому что
кто-то за этим следит.

Еженедельный прогон не избыточен: сигнатуры сканеров пополняются, и вчерашняя
«чистая» история сегодня может оказаться нечистой без единого нового коммита.

## Если сканер нашёл настоящий секрет

Порядок действий не интуитивный, поэтому по пунктам:

1. **Сначала отозвать и перевыпустить секрет, потом всё остальное.** С момента
   пуша он скомпрометирован; переписывание истории этого не отменяет, а лишь
   усложняет злоумышленнику поиск. Пока ключ не отозван, любые манипуляции с
   git — трата времени.
2. Убрать значение из рабочего дерева, заменив на чтение из окружения.
3. Вычистить из истории (`git filter-repo`) и force-push'ем перезаписать ветки
   **и** удалить/пересоздать затронутые PR — иначе значение останется доступно
   по `refs/pull/*`.
4. Если репозиторий уже публичный — попросить поддержку GitHub убрать
   недостижимые объекты и исходить из того, что значение уже проиндексировано.
5. Добавить в allowlist **только** если разбор показал, что это не секрет, — с
   причиной в описании записи. Allowlist без объяснения через полгода
   неотличим от «чтобы CI позеленел».
