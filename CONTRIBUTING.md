# Как участвовать

Спасибо за интерес к `jwt-service-app`. Баг-репорты, идеи и pull request'ы
принимаются от кого угодно, без предварительной договорённости. Ниже — всё, что
нужно знать, чтобы вклад дошёл до `master` без лишних кругов ревью.

Проект русскоязычный: документация, комментарии в коде и сообщения коммитов
пишутся по-русски. Issue и PR на английском тоже читаются и принимаются — код
важнее языка.

## Сначала — три исключения

1. **Нашли уязвимость — не открывайте issue.** Приватный адвайзори на GitHub
   (Security → Report a vulnerability) или письмо на
   [security@filipov.dev](mailto:security@filipov.dev). Полная политика, сроки
   и список того, что уязвимостью не считается, — в [SECURITY.md](SECURITY.md).
2. **Ключи и JWKS живут в другом репозитории.** Этот сервис ключи не генерирует
   и не хранит — за них отвечает `jwks-service-app`. Баг про ротацию, формат
   или хранение ключей заводите туда.
3. **Общение — по [Кодексу поведения](CODE_OF_CONDUCT.md).** Он короткий и
   сводится к «ведите себя как взрослый человек».

## Баг-репорты и предложения

Заводятся через [issues](https://github.com/filipov-dev/jwt-service-app/issues)
по шаблонам: **Баг** (нужны версия, конфигурация без секретов, шаги
воспроизведения, ожидаемое и фактическое поведение) и **Предложение** (нужна
задача, которую вы решаете, а не только желаемая реализация).

Перед тем как заводить, стоит посмотреть:

- [CHANGELOG.md](CHANGELOG.md) — возможно, починено в более свежем теге;
- раздел «Что уязвимостью не считается» в [SECURITY.md](SECURITY.md) и
  «Соглашения и подводные камни» в [AGENTS.md](AGENTS.md#соглашения-и-подводные-камни)
  — часть неожиданного поведения там осознанная и объяснена.

Вопрос «как это работает» тоже годится для issue: если ответ пришлось искать по
коду, значит, не хватает документации, и это баг документации.

## Окружение разработчика

Нужен Rust `stable` — канал и компоненты (`clippy`, `rustfmt`) заданы в
[`rust-toolchain.toml`](rust-toolchain.toml), rustup подхватывает файл сам.
Перед прогоном линта обновите тулчейн: `rustup update stable`. Канал ≠ версия,
CI ставит свежий stable на каждый прогон, и новые линты появляются там раньше,
чем в вашей локальной копии.

Кроме компилятора нужны Redis и `jwks-service-app`. Проще всего поднять весь
стенд разом — Docker Compose из [`deployments/dev/`](deployments/dev/docker-compose.yml)
(сервис, Redis, Redis Commander, Postgres, `jwks-service-app`, Swagger UI):

```bash
docker compose -p jwt-dev -f deployments/dev/docker-compose.yml up -d
```

Имя проекта (`-p jwt-dev`) задавайте явно: иначе Compose возьмёт имя папки —
`dev`, — а такая папка есть у многих сервисов сразу, и запуск может пересоздать
контейнеры чужого стенда.

## Команды

```bash
cargo build            # сборка
cargo test             # тесты (инлайн-модули #[cfg(test)] в исходниках)
cargo clippy --all-targets -- -D warnings   # линт ровно как в CI
cargo fmt --all        # форматирование
cargo audit            # уязвимости в зависимостях

UPDATE_OPENAPI=1 cargo test openapi   # перегенерировать docs/openapi.json
scripts/scan-secrets.sh               # gitleaks + trufflehog по всей истории
```

`cargo build --release` собирает тем же профилем, что прод-образ (`lto = "fat"`,
`codegen-units = 1`), и потому заметно дольше отладочной сборки. Для
повседневной проверки хватает `cargo build` и `cargo clippy`.

## Что проверяет CI

Пайплайн строгий, и падает он ровно на том, что можно прогнать локально:

| Workflow | Что делает |
|----------|-----------|
| `ci.yml` | `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --verbose` |
| `audit.yml` | `cargo audit` — уязвимость в зависимости блокирует мерж |
| `secrets.yml` | `scripts/scan-secrets.sh` — gitleaks и trufflehog по всем ссылкам, включая PR-рефы |

Любое предупреждение линтера и любое расхождение с `rustfmt` роняют сборку,
поэтому `cargo fmt` — перед коммитом, а не после ревью. Осознанно игнорируемые
advisory заносятся в [`.cargo/audit.toml`](.cargo/audit.toml) с
комментарием-причиной; ложные срабатывания сканеров секретов гасятся **только по
значению**, а не по пути к файлу (allowlist на каталог ослепляет сканер на
настоящий секрет, закоммиченный туда же).

PR с форка проходит те же три workflow: они не обращаются к `secrets.` ни разу
и потому безопасно запускаются на чужой код. Workflow с доступом к секретам
(`docker.yml`, `release.yml`) на PR не запускаются вовсе. Подробнее — в
[аудите CI](docs/security/workflow-audit.md).

## Соглашения по коду

- **Держите структуру модулей.** Крипто- и JWT-логика — в `src/key.rs` и
  `src/models/jwt.rs`, HTTP-слой — в `src/handlers.rs`. Карта модулей — в
  [AGENTS.md](AGENTS.md#карта-модулей-src).
- **Тесты пишутся рядом с кодом**, в `#[cfg(test)]`-модуле того же файла;
  модулей без тестов в проекте нет. Тест не должен зависеть от окружения,
  оставленного соседями: `TokenHeaders::create_new` читает `TOKEN_ALGORITHM`,
  поэтому в юнит-тестах берите `headers_with_alg` с явным алгоритмом.
- **Добавили эндпоинт** — добавьте аннотацию `utoipa::path`, зарегистрируйте
  путь и схемы в `ApiDoc` (`src/openapi.rs`) и перегенерируйте спеку
  (`UPDATE_OPENAPI=1 cargo test openapi`). Файл сверяется с кодом тестом
  `spec_file_is_up_to_date`, и разошедшийся роняет CI.
- **Добавили внутреннюю ручку** — впишите её в `internal_endpoints()` в
  `src/main.rs`. Тест уровней доступа шлёт туда запрос с валидным proxy-secret,
  но без TOTP, и ждёт `401`; без записи в список ручка окажется непроверенной, а
  ошибка «уровень 2 вместо 3» проверкой «без кредов → 401» не ловится.
- **Комментарий объясняет «почему», а не «что».** В коде и документации проекта
  зафиксированы причины решений (почему выключен `http2`, почему TLS-стек ровно
  один, почему `404` вместо `401` на `/metrics`) — если ваша правка отменяет
  такое решение, отмените и объяснение, а не оставляйте его противоречить коду.
- **Новые зависимости — только permissive** (MIT / Apache-2.0). Copyleft-крейты
  в проект не тянем: образы раздаются публично. Дефолтные фичи у крупных
  зависимостей перечисляются в `Cargo.toml` явно — иначе обновление молча
  включает новую фичу.

## Коммиты

Сообщения — [conventional commits](https://www.conventionalcommits.org/ru/) с
ключом задачи в скобках:

```
docs: CONTRIBUTING, кодекс поведения и шаблоны issue/PR (JWT-58)
fix: не терять jti при недоступном Redis (JWT-77)
feat!: переезд формата refresh-токена на v2 (JWT-90)
```

Типы: `feat`, `fix`, `docs`, `perf`, `refactor`, `test`, `ci`, `style`. Тип
определяет раздел [CHANGELOG.md](CHANGELOG.md), `feat!` выносит изменение в
«Ломающие изменения». **Subject попадает в CHANGELOG дословно** — пишите его как
строчку changelog'а, а не как записку себе. Сам `CHANGELOG.md` руками не правят:
его собирает [`scripts/changelog.sh`](scripts/changelog.sh) из истории коммитов,
и тот же скрипт наполняет описание GitHub Release.

**Версия в `Cargo.toml` поднимается каждым коммитом** по semver: major — сломана
совместимость, minor — новый функционал, patch — багфикс, рефакторинг, правки
документации и CI. Версия уезжает в `info.version` OpenAPI-спеки, поэтому после
подъёма перегенерируйте `docs/openapi.json`. Если правило кажется вам лишним
для вашей правки — не поднимайте, мейнтейнер поднимет при мерже; расхождение
спеки и версии в этом случае тоже поправит он.

## Pull request

Ветка отводится от `master` (он же единственная линия разработки), имя — по
задаче или по сути правки. Перед тем как открывать PR:

- [ ] `cargo fmt --all` и `cargo clippy --all-targets -- -D warnings` — чисто;
- [ ] `cargo test` — зелёные, новый код покрыт тестами рядом;
- [ ] спека перегенерирована, если менялись ручки, схемы или версия;
- [ ] версия в `Cargo.toml` поднята;
- [ ] документация поправлена вместе с кодом: изменили поведение —
      изменили `AGENTS.md`/`README.md`, а не «допишем потом»;
- [ ] секретов в диффе нет.

В описании PR — что изменилось и **почему**, ссылка на issue или задачу, и что
именно вы прогнали локально. Дифф удобнее ревьюить маленьким: три несвязанные
правки лучше тремя PR, чем одним.

Чего в PR быть не должно:

- **`pull_request_target`** в workflow — этого триггера в репозитории нет
  намеренно, и попутной правкой он не вводится;
- **секретов и приватных ключей** — креды CI лежат в GitHub Secrets;
- **`panic = "abort"`** в профиле релиза — он убьёт канал паник в GlitchTip;
- правок `CHANGELOG.md` руками — файл генерируемый.
