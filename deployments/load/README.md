# Нагрузочный тест `POST /tokens/verify`

Замер пропускной способности самой горячей публичной ручки сервиса. Нужен,
чтобы у оптимизаций горячего пути были цифры, а не намерения: **JWT-24**
(переиспользование соединения Redis) и **JWT-25** (кеш JWKS) меняют именно то,
что здесь измеряется.

Порядок такой: снять baseline **до** правок, повторить прогон после и сравнить.

## Состав

| Файл | Назначение |
|------|-----------|
| `docker-compose.yml` | Изолированный стенд зависимостей: Redis, Postgres, `jwks-service-app`. |
| `verify.js` | Сценарий k6: постоянная нагрузка на `POST /tokens/verify`. |
| `run.sh` | Прогон целиком: выпуск токенов, замер, сводка по метрикам. |

Ставить k6 на хост не нужно — `run.sh` запускает его контейнером.

## Прогон

### 1. Зависимости

```bash
docker compose -f deployments/load/docker-compose.yml up -d
```

Стенд поднимается под именем проекта `jwt-load` и на смещённых портах
(Redis `16379`, Postgres `15432`, JWKS `18082`) — он намеренно не пересекается
с `deployments/dev` и с прочими локальными стендами.

### 2. Сервис

Только release-сборкой: debug-профиль искажает результат в разы.

```bash
cargo build --release
```

```bash
RATE_LIMIT_VERIFY_ENABLED=false HOST=127.0.0.1 PORT=8080 REDIS_URL=redis://127.0.0.1:16379 JWKS_SERVICE_URL=http://127.0.0.1:18082 AUTH_PROXY_SECRET=dev-proxy-secret AUTH_TOTP_SECRET=MRSWGYLSMUQGO33WNFXGO4ZAOBWGKYLSFVRW63LOMNXW2ZI AUTH_METRICS_TOKEN=dev-metrics-token RUST_LOG=warn ./target/release/jwt-service-app
```

Что здесь важно, помимо очевидного:

- **`RATE_LIMIT_VERIFY_ENABLED=false`** — обязательно. С дефолтным per-IP
  лимитом (10 rps на адрес) прогон упрётся в 429 и померяет rate limiter, а не
  сервис. `run.sh` предупредит, но выключить лимит может только запуск сервиса.
- **`AUTH_METRICS_TOKEN`** — без него ручка `/metrics` не публикуется вовсе, и
  сводка останется без главных чисел (походы в JWKS и Redis).
- **`RUST_LOG=warn`** — на уровне `info` каждый запрос пишет строку в stdout, и
  под нагрузкой это само по себе становится статьёй расхода.

### 3. Замер

```bash
./deployments/load/run.sh
```

Параметры — через переменные окружения: `VUS` (по умолчанию 50), `DURATION`
(`30s`), `TOKENS` (20), `TARGET_URL` (`http://127.0.0.1:8080`).

### 4. Уборка

```bash
docker compose -f deployments/load/docker-compose.yml down -v
```

## Что читать в выводе

`run.sh` печатает RPS и латентности (p50/p95/p99/max), а под ними — два числа,
ради которых всё и затевалось:

- **запросов к JWKS на верификацию** — сейчас это ≈1: `KeyManager::get_jwk`
  создаёт новый HTTP-клиент и тянет весь JWKS на каждый запрос (JWT-25). После
  кеша должно стать почти 0.
- **команд Redis на верификацию** — сейчас каждая команда идёт по свежему
  соединению (JWT-24). Число команд не изменится, изменится их цена — она
  видна по латентности.

## Оговорки

Замер снимается на одной машине: клиент, сервис и зависимости делят CPU, а
`jwks-service-app` и Postgres поднимаются в Docker (на macOS это ещё и
виртуальная машина). Абсолютные значения поэтому не переносятся на прод — они
годятся только для сравнения «до/после» на одном и том же стенде. Чтобы
сравнение было честным, прогоны должны идти на одной машине, в одной
конфигурации и желательно подряд.
